# Stepwise Execution Plan

Gates, evidence, and decisions from pilot to release

# 1. How to use this plan
Proceed in dependency order. A checkpoint is a documented decision with evidence and an owner; elapsed time does not imply completion. HOLD means uncertainty or missing evidence; FAIL means a violated requirement. Both block dependent work until a corrective plan is accepted. Reversible exploratory work may continue only if it cannot contaminate locked evaluation.
Stage definitions in this package are newly proposed because the full original conversation was unavailable. The phase sequence below is the authoritative implementation sequence for protocol v1.0 once the scientific lead freezes it.
# 2. Phase 0 — protocol and resource freeze
Owner: scientific lead with statistics and runner owners. Read all four memos, resolve target estimands, set hardware budget and intended claims, and version the config schema. Register screening cells and reserve confirmatory test manifests separately. Record where test labels live and who can access them.
Deliver: protocol_v1.json; experiment registry; contrast family; metric dictionary; seed policy; budget worksheet; software lockfile; access policy. No model training is needed at this checkpoint.
Checkpoint CP00: PASS only when ARS, oracle information, physical target, split units, multiplicity family, failure states, and maximum GPU-hours have explicit values. Decision: accept defaults or amend them before observing effects. HOLD if hardware availability or budget is unknown; a low-cost pilot may be approved with its own explicit cap.
# 3. Phase 1 — simulator and matched-state validation
Owner: simulator. Implement free flight first, render a small nuisance-balanced corpus, and compare trajectories to analytic ground truth. Validate continuous time, camera visibility, scale and gravity sign. Generate matched-state bundles by backward/forward construction; compare exact anchor states and rendered anchor images.
Deliver: simulator acceptance report; 30 representative annotated clips; error-versus-step-size plot; support/rejection audit; group-level fixture; versioned renderer config. Contact and pendulum validation can run later but must pass before Stage D.
Checkpoint CP01: maximum analytic position error <1e−6 m for primary free flight, anchor state error <1e−6, identical anchor pixels within a group, no scored collisions, shared visible support. Decision: freeze simulator v1; otherwise repair physics/support and regenerate. No model result can compensate for failure here.
# 4. Phase 2 — datasets and leakage audit
Owner: dataset. Create tiny integration data, then 5k pilot corpora. Split groups/assets before rendering. Freeze normalizations from training only. Verify all law variants of a group occupy one split. Hash all files and save seed derivations.
Deliver: dataset.json; manifest and filtered training view; checksums; split counts; law×nuisance tables; single-frame law-classifier audit; common-support report. Confirmatory test may be generated now but remains locked.
Checkpoint CP02: zero group overlap, balanced nuisance sampling by design, complete group coverage, deterministic regeneration in pinned environment, no hidden metadata entering the loader. Single-frame classifier performance above chance triggers investigation of residual state or nuisance information; it is not automatically a leak unless the matched-state test or nuisance balance is violated. Decision: admit dataset or repair/regenerate all affected groups.
# 5. Phase 3 — physical baselines and identifiability
Owner: evaluation. Run analytic state Bayes predictor and law oracle before training JEPA. Fit the privileged acceleration estimator and supervised visual inferability diagnostic. Measure G across context/horizon/switch regimes. Verify random future switches are unknown to the primary oracle.
Deliver: baseline losses; initial usefulness–inferability grid; oracle residual report; null/ambiguous-history fixtures; bootstrap code acceptance tests. State and oracle use exactly the same scored targets and weights as JEPA will use.
Checkpoint CP03: primary fixed-law oracle residual <1e−8 normalized MSE; variable-law matched-state gap above proposed epsilon in at least one candidate regime; ambiguous fixtures behave as expected; switched-law oracle converged to a documented numerical tolerance. Decision: choose eligible pilot regimes using validation; if gap absent, fix task horizon/support, not scoring after test access.
# 6. Phase 4 — JEPA and end-to-end pilot
Owner: JEPA with runner and reporting. Run tiny overfit/shape tests, future-isolation and EMA tests, train pilot models, freeze encoder, fit all readouts with equal tuning budget, evaluate, bootstrap and fill a copy of the dashboard. Record seconds/update, peak memory and rendering throughput.
Deliver: resumable checkpoint; training curves; rank/variance diagnostics; readout learning curves; one full provenance chain; dry-run dashboard clearly labeled PILOT; compute projection for A–E. Use fixture or pilot data only.
Checkpoint CP04: tests pass; no target leakage or collapse; loss and readout diagnostics make sense; retry/resume works; uncertainty pipeline recovers synthetic known effects; projected budget approved by project owner. Decision: freeze objective and optimizer. A pilot need not show positive ARS to pass implementation, but a persistently invalid task or failed optimization blocks scale-up.
# 7. Stage A — locate useful and inferable regimes
Owner: runner/evaluation. Execute the 20 registered cells (context×horizon plus fixed-law controls), four training runs/cell for screening. Reuse paired datasets where appropriate. Report fixed-law training both on its in-distribution test and the shared variable-law test; the latter is an OOD learning-environment contrast, not an in-distribution comparison.
Deliver: c×h ARS heat map with eligibility masks; raw losses and gap; gravity-inferability curves; seed/corpus variation; negative controls; accepted/failed run inventory. All figures include both frame counts and seconds.
Checkpoint CPA: baseline/oracle verified, sufficient valid cells, no selective failure pattern, history effects separated from oracle-gap changes. Decision: lock one primary c/h regime for fresh confirmation and preselect Stage D/E checkpoints by validation. If effect is absent with a narrow CI, record a null at this scope; if uncertain, refine precision before expanding.
# 8. Stage B — diversity and persistence
Owner: runner/statistics. Execute 34 nominal cells, including variance-matched diversity controls. Verify realized dwell distributions and number of observable switches. K=1 persistence cells are duplicates in physical content; reuse only if resolved configs and datasets establish equivalence and record aliasing explicitly.
Deliver: law-diversity×persistence tables; usefulness/inferability panels; conditional history benefit; continuous-law interpolation tests; transition-oracle audit. Analyze interaction between context and persistence rather than impose a single monotone trend.
Checkpoint CPB: no confounding between dwell and horizon definition; changing-law oracle is non-clairvoyant; K comparisons show law variance; CIs and missingness available. Decision: retain or reject H2/H3 within tested scope; select which persistence regimes justify further capacity work. Do not score ARS in zero-gap cells.
# 9. Stage C — depth, width, data, compute
Owner: scaling sweeps. Run 19 nominal cells. Depth×width includes nine cells. Data×compute includes nine with one shared reference. Add two depth controls approximately matched to reference encoder parameter count by choosing widths in multiples of 32 and recording the residual mismatch (target within 10%).
Deliver: ARS and raw-loss curves against depth, parameters, data, tokens, measured compute; matched-compute and fixed-update comparisons; timing/memory profiles; fit residuals; Pareto table. At fixed total compute, stop by estimated FLOP budget calibrated with measured throughput and report remaining error in matching. Data-size runs must report epochs/reuse because fixed updates imply unequal passes.
Checkpoint CPC: all resource quantities recorded, model variants healthy, comparison budgets explicit, no broad extrapolation from three points. Decision: identify a feasible model for transfer and choose whether a larger sweep is justified. A depth claim requires corroboration beyond the fixed-width curve.
# 10. Stage D — transfer and cause distinction
Owner: evaluation/representation. Validate pendulum and bounce simulators first. Evaluate three prespecified checkpoints at three label budgets on bounce, pendulum, and source-to-target mechanism reuse. Run the two cause suites with informative and deliberately ambiguous evidence. Freeze pretraining encoder throughout.
Deliver: transfer sample-efficiency curves; true-law/random/shuffled controls; gravity interpolation/extrapolation panels; cause-identifiability audit; layer probes and swap sensitivity. Report the extra readout supervision and all target-phenomenon information given to the model.
Checkpoint CPD: primary matched-state benefit valid; at least one prespecified transfer contrast meets its corrected evidence criterion for a reuse claim; observationally equivalent cause cases are explicitly recognized as non-identifiable. Decision: state exactly which level of the evidence ladder is reached. A failure here yields “history benefit without demonstrated cross-phenomenon reuse,” not a hidden positive abstraction claim.
# 11. Stage E — breaking frontier
Owner: breaking-frontier agent with statistics. Evaluate six axes at five levels per selected checkpoint, repeating boundary-relevant levels across the full evaluation seed set. Use one stress axis at a time before optional combinations. Distinguish model degradation from a shrinking usefulness gap or insufficient evidence.
Deliver: success/uncertain/failure/ineligible bands; last-success/first-failure brackets; per-level CIs; oracle curves; examples of failure modes; optional noise×dwell phase diagram. Adaptive levels are marked exploratory and do not replace the original grid.
Checkpoint CPE: every declared boundary is supported by eligible scores and uncertainty; non-monotonic axes have multiple intervals or no single boundary; no “failure” labels on missing runs. Decision: define tested operating envelope and next discriminating experiment.
# 12. Fresh confirmation and release
Owner: statistics then reporting. Freeze eight confirmatory cells and four primary contrasts using screening/validation only. Run 5 fresh corpus replicas × 3 fresh initialization seeds per cell. Unlock test once. Compute paired hierarchical intervals, multiplicity correction, and leave-one-corpus-out checks. A failed confirmation stays in the report alongside screening.
Deliver: immutable aggregate CSV/JSON; bootstrap samples; filled workbook; positive/negative/null memo; plots; run registry; missingness/failure appendix; code/data release manifest with hashes. Archive amendment history and original preregistration.
Checkpoint CPFINAL: all claims map to prespecified endpoints or are labeled exploratory; every figure resolves to accepted runs and group losses; workbook reproduces aggregate files; locked test was not used for model selection. Decision: release a scoped conclusion, a replication plan, or a null/inconclusive report. Completion does not require a positive finding.
# 13. Critical path and resource triage
Dependency chain: CP00 → CP01 → CP02 → CP03 → CP04 → CPA → CPB/CPC → CPD → CPE → fresh confirmation → CPFINAL. Statistics fixtures and dashboard construction can proceed alongside simulator work using clearly isolated synthetic fixtures. No test-dependent analysis starts before the relevant protocol freeze.
Budget triage order: preserve simulator/evaluation validity and primary confirmation; reduce optional reconstruction baseline, exploratory two-axis stress grid, and secondary layer analyses first. Reduce cell count through a documented amendment before observing locked outcomes. Never hide failed seeds, redefine ARS after a result, or substitute more frames for more independent training runs.
